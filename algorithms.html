The Shape Expressions (ShEx) language describes RDF nodes and graph structures, organized in a shapes schema. A shapes schema must comply to a series of requirements.

This document presents the algorithms that allow to test whether a syntactically correct shapes schema satisfies the requirements. It also presents algorithms for validating an RDF graph against a ShEx schema that satisfies the requirements.

This document is being developed by the Shape Expressions Community Group.

This version is an editor's draft.

Introduction

Algorithms for Checking the Schema Requirements

Shape Expression Reference Requirement

The definition of this requirement is in the shape expressions language specification.

For a ShEx schema sch, let ShapeExprIds(sch) be the set of shape expression identifiers in sch.

Algorithm checkShapeExpressionReferenceRequirement


Input: sch: a schema
Output: true sch satisfies the shape expression reference requirement, false otherwise
        whenever the latter is true, produces also  D: the shape expressions dependency graph induced by sch

let ShapeExprIds be the set of all shape expression ids in sch
let ShapeExprRefs be the set of all shape expression references in sch
if shapeExprRefs is not included in shapeExprIds then return false

initiate a directed edge labelled graph D which nodes are all Shape, NodeConstraint, ShapeNot, ShapeOr, ShapeAnd and shapeExprRef elements that appear in sch

foreach ShapeExpr se in the vertex set of D
    if se is a ShapeOr or a ShapeAnd then
        foreach ShapeExpr sub in se.shapeExprs
            add to D an edge from se to sub labelled with pos
    else if se is a ShapeNot then
        add to D an edge from se to se.shapeExpr labelled with neg
    else if se is a shapeExprRef then
        add to D an edge from se to shapeExprWithId(se) labelled with pos

if D contains a cycle then
    return false
else 
    return (true, D)

Algorithm for computing the dependency graph of a schema.


Input: schema a ShexSchema
Output: D the shape expressions dependency graph


let DSE be the dependency graph as computed by checkShapeExpressionReferenceRequirement
let DTE be the dependency graph as computed by checkTripleExpressionReferenceRequirement

let atomicTripleConstraints be the map that with every TripleExpression s.expression that appears in schema (for some Shape s) associates the set of TripleConstrants tc s.t. there is a path in DTE between s.expression and tc;

let atomicShapes be the map that with every ShapeExpression tc.valueExpr that appears in schema (for some TripleConstraint tc) associates the set of Shapes s s.t. there is path in DSE from tc.valueExpr to s

initiate a directed edge-labelled graph D with vertex set that contains all the Shapes in schema

foreach Shape s vertex of D s.t. s.expression is in the key set of atomicTripleConstraints
    foreach TripleConstraint tc in atomicTripleConstraints(s.expression)
        if tc.valueExpr is present then
            foreach Shape s2 that belongs to atomicShapes(tc.valueExpr)
                if there is at least one path in DSE from tc.valueExpr to s2 that traverses an odd number of neg-labelled edges then
                    add to D a neg-labelled edge from s to s2
                else
                    add to D a pos-labeled edge from s to s2

return D

Algorithm for computing the stratification of a schema.


Input: schema a ShexSchema
Output: a map stratum from the set of Shapes in schema to natural numbers, or ERROR if the schema cannot be stratified

let D be the dependency graph of schema

if D contains a strongly connected component stc that contains a neg-labelled edge then
    raise an error

let S be a directed graph which set of vertices is the set of strongly connected components of D
let L be a topological sorting of the vertices of S

foreach s node of D
    let stratum(s) be the index in L of the unique strongly connected component stc s.t. s belongs to stc

return stratum

Algorithms for Validation

Validation as a Search over Matchings

The algorithms in this section orchestrate calls to satisfies(n, s, G, sm): refine validation evaluates it for every (node, shape) pair, stratum by stratum; recursive validation evaluates it on demand. When s is a Shape with triple expression E, deciding satisfies is itself a search problem: does some assignment ("matching") of the relevant neighbourhood triples of n to the triple constraints of E satisfy E's cardinalities and grouping (EachOf, OneOf)? With EXTENDS, the neighbourhood must additionally split among the shapes of the extension hierarchy so that every supertype's own triple expression accepts its share.

The direct reading of that decision problem is: for each triple constraint, which triples could possibly satisfy it? — a map from triple constraints to candidate triples. But a matching is a choice, not a relation: every triple must end up assigned to exactly one triple constraint (or shown to be excused by EXTRA or absent altogether). Turning the constraint-indexed relation into a triple-indexed function — one candidate constraint chosen per triple — is what makes "matching" a well-formed combinatorial object that can be enumerated, pruned and verified. Three related structures recur below. Given the neighbourhood triples T of the node and the triple constraints TC of a (possibly EXTENDS-composed) triple expression:

pre-matching
a map T → 2^{TC}: with every triple, the set of triple constraints it could be assigned to — same predicate, and (recursively) the triple's value satisfies the constraint's value expression. For a fixed triple constraint tc, its candidate triples are recovered as { t ∈ T : tc ∈ preMatching(t) } — the "triple constraint → set of triples" view the reader may start from.
matching
a map T → TC choosing, for every triple, exactly one of its pre-matching candidates. A pre-matching is a compact representation of the set of matchings obtainable by choosing one candidate per triple — the Cartesian product ∏_t preMatching(t). The search is organized in this triple-indexed form because there, "assign every triple exactly once" is a syntactic guarantee rather than a side condition to check.
split
the inverse of a chosen matching: a map TC → 2^T (or, grouped one level further, shapeLabel → 2^T for an EXTENDS hierarchy) recovering, for a specific matching, which triples ended up on which constraint. This is the view a cardinality check needs ("how many triples did tc receive?"), and the view against which EXTENDS constraints and semantic actions are evaluated.

Algorithm for deciding satisfies(n, s, G, sm) for a Shape s, by exhaustive enumeration of matchings.


Input: an RDF graph G, a node n, a Shape s with triple expression E, a shape map sm
Output: true if some matching of the relevant neighbourhood of n satisfies E, false otherwise

let TCs be the set of triple constraints of E (with EXTENDS, of every triple expression of the hierarchy)
let matchables be the set of triples (n,p,o) in G s.t. p is the predicate of some tc in TCs,
    plus the triples (o,p,n) s.t. ^p is the predicate of some inverse tc in TCs

foreach t = (n,p,o) in matchables
    let cands(t) = { tc in TCs : tc.predicate = p and
                     (tc has no valueExpr, or o satisfies tc.valueExpr under sm) }

foreach t in matchables with cands(t) = {}
    if t.predicate is not in s.extra then return false
    remove t from matchables

foreach matching m in the Cartesian product over t in matchables of cands(t)
    let bag(m) be the map tc -> number of triples t s.t. m(t) = tc
    if bag(m) is accepted by E then       // exact check: cardinalities, EachOf grouping, OneOf choice
        return true                       // m also fixes the split consumed by EXTENDS
                                          // constraints and by semantic actions
return false

The enumeration line is a Cartesian product: k triples with 2 candidates each yield 2^k candidate matchings, and whenever triple constraints share a predicate — across OneOf alternatives, across the shapes of an EXTENDS hierarchy, or between a shape and its EXTRA-tolerated context — most of those matchings are doomed for reasons visible long before each is individually verified. refines this algorithm with two pruning techniques that leave its answers — indeed its entire set of accepted matchings — unchanged.

Refine Validation

Algorithm for refine validation.


Input: an RDF graph G, a ShexSchema schema which set of shapes is S
Output: the shape map completeTyping(G,sch)

let stratum=stratification(sch)
let k be the greatest number in the range of stratum

let typing be the empty set
for i in 0 .. k do
    let shapes-i be the set of Shapes s in S s.t. stratum(s) = i
    let typing-i = nodes(G) x shapes-i
    do
        changing = false
        foreach (n,s) in typing-i do
            if not matches(n,s,G,Sch,typing-i union typing)
                remove (n,s) from typing-i
                changing = true
    while (changing)
    add typing-i to typing
end for    

return typing

Recursive Validation

Algorithm isValid(G,sch,n,se) for checking a unique node s against a unique shape expression s.


Input: RDF graph G, ShexSchema sch with set of Shapes S, node n in G, Shape s in sch, hyp: a stack over Nodes(G)xS
Output: true if satisfies(G,sch,n,s,completeTyping(G,sch)), false otherwise

push (n,s) on hyp
let sm be an empty shape map

let atomicTripleConstranits be the set of atomic triple constraints of s.expression
let neighbourhood be the set of (predicate,n2) s.t. either (n, predicate, n2) in G and predicate appears in a triple constraint in allTC, or (n2, predicate, n) in G and ^predicate appears in a triple constraint in allTC

for (pred,n2) in neighbourhood do
    foreach tc in allTC
        if tc.predicate == pred then
            if tc.valueExpr is present then
                foreach s2 in atomicShapes(tc.valueExpr)
                    if isValid(G,sch,n2,s2) then
                        add (n2,s2) to sm

add all elements of hyp to sm
result = satisfies(n,s,G,sm)
pop from hyp

return result

Recursive validation algorithm.


Input: an RDF graph G, a ShexSchema schema which set of shapes is S, an initial shapeMap map
Output: true if satisfies(n,s,G,sch,completeTyping(G,sch)) for every (n,s) in map, false otherwise

let sm be an empty shape map

foreach (n,se) in map
    foreach Shape s in atomicShapes of se
        if isValid(s,n,G,sch) then
            add (n,s) to sm
    if not satisfies(n,se,G,sch,sm) then
        return false

return true

Pruning the Matching Search

The two refinements below prune the enumeration algorithm of without changing its answers: each only ever discards candidate matchings that the exact verification would also have rejected, so the set of accepted matchings — and everything downstream of it (EXTENDS splits, semantic actions) — is untouched. Some search is unavoidable: for expressions with repeated triple constraints, deciding bag membership is NP-complete [[shex-complexity]], and even where polynomial decision procedures exist, a practical validator streams concrete witness matchings — of which there can be exponentially many — because downstream checks consume the specific triples matched. Both refinements are implemented in Apache Jena's jena-shex module, from which the measurements below are taken.

Negative Caching: Prune Refuted Candidate Pairs

The pre-matching construction already contains the first pruning: computing cands(t) once, upfront, for every (triple, candidate constraint) pair — one recursive value-expression check per pair — and never revisiting a pair that failed. Informally this is a negative cache: rather than re-discovering, inside every candidate matching that happens to try the pair again, that the triple's value does not satisfy the constraint, the failure is recorded once against the pre-matching itself and the pair never enters the search. A validator that instead evaluates value expressions while walking each candidate matching re-pays that cost once per matching — multiplied by however many candidate matchings the rest of the neighbourhood generates (measured concretely in ).

The same contract generalizes from values to structure: a candidate can also be refuted because committing even one triple to it can never lead to an accepted matching — a co-occurrence obligation elsewhere in the expression that the data cannot meet, a OneOf exclusivity already violated, or a maximum cardinality already exceeded. Both forms have the same shape: delete a (t, tc) pair the moment it is known to appear in no accepted matching, so no refutation is ever derived twice. The structural form is the subject of the next section.

Bag-Directed Search with Partial-Bag Refutation

Whether a triple expression accepts a matching depends only on the matching's bag — the count of triples assigned to each triple constraint; which specific triple went where matters only to downstream consumers (splits, semantic actions). And once the pre-matching is computed, two triples with the same candidate set are interchangeable in any bag. So: group the triples into classes by candidate set, and search over count vectors — how many triples of the class go to each of its candidates — instead of over individual assignments. A class of n triples over k candidates has \binom{n+k-1}{k-1} count vectors, polynomial in n for fixed k, in place of k^n assignments. Concrete matchings are produced only for bags that survive, by enumerating the multiset permutations within each class.

During the search, each triple constraint tc carries an interval [lo(tc), hi(tc)]: lo counts the triples already committed to it by decided classes, and hi = lo + the total size of the undecided classes that still offer tc as a candidate. A test refute(lo, hi), computed compositionally over the expression tree, answers: is no exact bag between lo and hi (pointwise) accepted? It is a sound necessary-condition test — true proves the entire region hopeless, since every bag reachable by finishing the search lies between the current lo and hi, while false proves nothing and leaves the verdict to the exact verification of complete bags. It accounts for minimum and maximum cardinalities, EachOf co-occurrence obligations, and OneOf exclusivity — including that exclusivity does not survive repetition: each iteration of (:a . | :b .)+ chooses its alternative independently. (The Jena implementation calls this test feasibility; this document says refutation, since refuting is the only verdict it delivers definitively.)

The test is applied at two moments. Upfront, as an arc-consistency pass: for every candidate (t, tc) pair, if committing a single triple to tc is already refutable under the most optimistic hi, delete tc from the whole class at once — the structural generalization of negative caching. And once per search node: after committing each class's count vector, either the remaining region is refuted (backtrack) or the search descends. If arc consistency empties a class's candidate set, the shape fails outright: a triple that value-matches some constraint can never be left unmatched — EXTRA only excuses triples that matched no constraint to begin with.

refute deliberately ignores constraints that per-constraint intervals cannot express: count coupling inside a repeated group ((:a . ; :b .)+ requires equal counts of :a and :b) and divisibility ((:a . {2,2})* accepts only even counts). Bags that survive are therefore always verified exactly, once, before acceptance; the refinement loses no correctness, only doomed work.

The enumeration algorithm of , with the refinement's additions highlighted:


Input: an RDF graph G, a node n, a Shape s with triple expression E, a shape map sm
Output: as for enumeration - the same matchings are accepted; only the work spent differs

let TCs, matchables and cands be as in the enumeration algorithm
                                          // computing cands() once, upfront, is the negative
                                          // cache: a refuted (t,tc) pair is never revisited
foreach t in matchables with cands(t) = {}
    if t.predicate is not in s.extra then return false
    remove t from matchables

partition matchables into classes: class(C) = { t : cands(t) = C }
repeat until no candidate is removed:                       // arc consistency
    foreach class C and candidate tc of C
        if refute(lo = one triple on tc, hi = every triple on all of its candidates)
            remove tc from C's candidates
if some class has no candidates left then return false
                      // a triple that value-matches some tc can never be left unmatched,
                      // so EXTRA does not excuse a class emptied by refutation

search depth-first over the classes, fewest candidates first:
    at each class C, enumerate the count vectors over C's candidates summing to |C|,
        each count capped by the candidate's declared maximum
    after committing a count vector: if refute(lo, hi) then backtrack
each leaf of the search determines a bag w over TCs
    if w is accepted by E then            // exact check, unchanged
        foreach matching m realising w  // multiset permutations within each class
            return true                   // m fixes the split consumed by EXTENDS
                                          // constraints and by semantic actions
return false

Worked Example: a FHIR Research Blood-Pressure Profile

The two refinements address different failure modes, and a schema built entirely from one of them shows only one at work. The following profile — modelled on a research blood-pressure Observation profile in HL7 FHIR — needs both at once. It is illustrative rather than clinically certified, but the moving parts are real FHIR: repeated component and referenceRange elements, and range bounds that are FHIR Quantity structures carrying a value, an optional comparator and a UCUM unit code such as mm[Hg]. Shape labels use the document-relative <#Label> pattern, resolved against the schema document's base IRI.

The profile accepts submissions from two data-collection protocols, distinguished along two independent axes. A quick capture records one or two component entries and nothing more; an extended capture records any number of components but must include a protocol quality-control flag. Independently, the reference ranges are either a short list (one or two) of guideline ranges, or a longer list plus exactly one critical range whose bounds mark the panic thresholds. Neither axis is declared explicitly; the validator works each out from what is present.

By predicate alone, the pre-matching of ex:obs1 is t1–t3 → {tc1, tc2}; t4 → {tc3}; t5–t7 → {tc4, tc5, tc6} — a Cartesian product of 2·2·2·1·3·3·3 = 216 matchings.

Negative caching checks each (range, candidate) pair once, recursively: ex:sysNormal (t5) against S3 fails inside its low Quantity (90 < 120), deleting tc6; likewise t6. ex:panic (t7) against S2 fails the guideline low window (120 > 90), deleting tc4 and tc5. The pre-matching becomes t5,t6 → {tc4, tc5}; t7 → {tc6}: 2³·2² = 32 matchings — and no value expression is ever evaluated again.

The classes are {t1,t2,t3} over {tc1, tc2}; {t4} over {tc3}; {t5,t6} over {tc4, tc5}; and {t7} over {tc6}. The two singleton classes are forced, and committing them drives the refutation test: with tc3 occupied, te1's first alternative — which requires the second alternative's constraints to stay empty — is refuted, so every count vector placing components on tc1 is cut: t1–t3 all go to tc2. Symmetrically, t7 on tc6 forces t5 and t6 onto tc5. Exactly one bag survives the search, and its expansion is a single matching, whose split is:

Counting everything — the focus-node search plus every recursive check of a range or Quantity node against a candidate shape — the whole validation verifies 16 (sub-)matchings, measured, against the 32 focus-node matchings alone that post-caching enumeration walks, or the 216 that a validator evaluating value expressions inside the walk would explore.

Now scale the same schema: n_c components (and no quality flag) with n_r reference ranges, every range guideline-valued and none critical-valued. No instance with n_c ≥ 3 conforms, so nothing short-circuits — the worst case for any search. Negative caching deletes tc6 from every range, at a one-time cost of 6 verified sub-matchings per range (the tc4 and tc5 checks each verify two Quantity nodes and the range node itself; the tc6 check is refuted inside the low Quantity before any sub-matching is assembled). Arc consistency then deletes tc5 from every range — committing any triple to it requires tc6 to be occupiable, but hi(tc6) = 0 — and tc2 from every component, since there is no quality-flag triple to occupy tc3. Every class collapses to its {1,2}-bounded candidate; for counts of 3 or more no count vector fits, and the search produces no bag at all: zero focus-node matchings.

Summary

  • Organize the search triple-indexed (a candidate-constraint set per triple, one choice per triple), and recover the constraint-indexed split from each chosen matching for the checks that need it.
  • Refute once, never re-derive: by value (the negative cache) when the pre-matching is built, and by structure (partial-bag refutation) at class granularity upfront and at every search node thereafter.
  • Search count vectors over classes of interchangeable triples; verify surviving bags with the exact check, and expand a bag into concrete matchings only then.
  • Both prunings are necessary-condition filters: the set of accepted matchings is invariant; only the amount of work spent discovering it changes.
