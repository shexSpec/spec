Validating a node against a shape with a triple expression requires deciding whether some assignment of the node's neighbourhood triples to the triple expression's triple constraints satisfies the expression's cardinalities and grouping structure — additionally split across a hierarchy of shapes when EXTENDS is involved. This document explains, for implementors, the data structures used to represent that assignment problem and, through one worked example with a deliberately large search space, two techniques that make the search tractable in practice: pruning a triple's candidate constraints once a candidate is refuted (informally, "negative caching"), and searching over count distributions ("feasibility bags") instead of over individual triple-to-constraint assignments, pruned by a sound but inexpensive feasibility test. The techniques are implementation-independent; this document is illustrated with references to the Apache Jena jena-shex implementation, where they are implemented and empirically measured.

This document is being developed by the Shape Expressions Community Group. It is an implementors' note: informative, not normative. It records an implementation technique observed to preserve the accepted-matching semantics defined by the Shape Expressions Language specification and analyzed by the algorithms document, while making validation tractable on schemas and data where the naive search is exponential.

This version is an editor's draft.

Introduction

To decide whether a node n satisfies a shape with triple expression E, partition-based ShEx semantics asks whether some assignment ("matching") of the relevant neighbourhood triples to the triple constraints of E satisfies E's cardinalities and grouping (EachOf, OneOf). With EXTENDS, the neighbourhood must additionally split among the shapes of the extension hierarchy so that every supertype's own triple expression accepts its share.

The direct reading of that decision problem is: for each triple constraint, which triples could possibly satisfy it? — a map from triple constraints to candidate triples. But a matching is a choice, not a relation: every triple must end up assigned to exactly one triple constraint (or shown to be excused by EXTRA or absent altogether). Turning the constraint-indexed relation into a triple-indexed function — one candidate constraint chosen per triple — is what makes "matching" a well-formed combinatorial object that can be enumerated, pruned, and verified. §2 makes this precise; it is the partitioning scheme referred to throughout this document.

Enumerating that function naively is a Cartesian product: if k triples each have 2 candidate constraints, there are 2^k candidate matchings to check, the overwhelming majority of which are doomed for reasons visible long before they are fully checked. §5 works a single schema — a FHIR-flavoured research blood-pressure profile — through both the naive algorithm and the optimized one, at increasing data sizes, to make the difference concrete: at 32 candidate triples the naive algorithm would check 4294967296 candidate matchings; the optimized one checks 32, correctly, in about a millisecond. That the optimized figure is 32 and not 0 is itself informative — it is exactly where the two techniques' distinct jobs become visible: one part of the schema is refuted purely by value (a fixed, linear cost independent of how ambiguous the rest of the schema is), the other purely by structure (collapsing to zero, however large it grows).

The partitioning scheme: from candidate constraints to a chosen matching

Three related structures recur through this document and through any partition-based validator. Given a node's neighbourhood triples T and the triple constraints TC of a (possibly EXTENDS-composed) triple expression:

pre-matching
a map T → 2^{TC}: with every triple, the set of triple constraints it could be assigned to — same predicate, and (recursively) the triple's value satisfies the constraint's value expression. This is the natural, constraint-indexed-in-spirit starting point: for a fixed triple constraint tc, its candidates are { t ∈ T : tc ∈ preMatching(t) } — the "triple constraint → set of triples" view the reader may start from.
matching
a map T → TC choosing, for every triple, exactly one of its pre-matching candidates. A pre-matching is a compact representation of the set of matchings obtainable by choosing one candidate per triple — the Cartesian product ∏_t preMatching(t). This is the partitioning scheme by which this document (and the reference implementation's MatchingsIterator / FeasibleMatchingsIterator) organizes search: one candidate choice per triple, not one triple set per constraint, because only the triple-indexed form is guaranteed to assign every triple exactly once.
split
the inverse of a chosen matching: a map TC → 2^T (or, grouped one level further, shapeLabel → 2^T for EXTENDS hierarchies) recovering, for a specific matching, which triples ended up on which constraint. This is the view a cardinality check needs ("how many triples did constraint tc receive?"), and the view EXTENDS constraints and semantic actions are evaluated against. It is computed once a matching has been chosen, by literally inverting the T → TC map.

In short: the search is organized as T → TC because that is the form in which "assign every triple exactly once" is a syntactic guarantee rather than a side condition to check; the result is read back as TC → 2^T because that is the form the cardinality and EXTENDS/semantic-action checks are stated over. Concrete instances of both views appear in the worked example below (§5.2).

Pruning refuted candidates ("negative caching")

Before any matching is enumerated, every (triple, candidate constraint) pair in the pre-matching is checked once: does the triple's object (or subject, for an inverse constraint) satisfy the constraint's value expression? If not, the constraint is removed from that triple's candidate set — permanently, for the remainder of this validation. Informally this is a negative cache: rather than re-discovering, inside every candidate matching that happens to try the pair again, that it fails, the failure is recorded once against the pre-matching itself, and the search never revisits it.

This value-level pruning generalizes to a structural one, described in §4: a candidate can also be refuted because committing even one triple to it can never lead to an accepted matching, for reasons that have nothing to do with any single triple's value — a co-occurrence obligation elsewhere in the expression that the data cannot meet, an exclusivity rule (OneOf) already violated, or a maximum cardinality already exceeded by triples committed elsewhere. Both forms of pruning have the same shape: delete a (t, tc) pair once it is known to appear in no accepted matching, so the search never spends time rediscovering that fact once per candidate matching that would have tried it.

Feasibility bags: searching distributions instead of assignments

Two further ideas turn the remaining candidate space from exponential-in-triples to, in the case that matters most, non-existent.

Group triples with identical candidate sets into classes

A validator that has already computed the pre-matching (§2) knows, for every triple, its exact candidate set. Two triples with the same candidate set are interchangeable for the purpose of deciding whether a satisfying matching exists: any check that consumes only the multiset ("bag") of constraints occupied by a matching — which is what the interval-based validity check does — cannot tell them apart. Group triples into classes by candidate set, and search over how many triples of a class go to each of its candidates (a composition: a count vector summing to the class size) instead of over which specific triple goes where.

A class of n triples with k candidates has \binom{n+k-1}{k-1} compositions — polynomial in n for fixed k — in place of k^n individual assignments. Concrete assignments are only produced afterwards, for compositions that survive the feasibility test below, since checks external to the bag itself (EXTENDS constraints on the split, semantic actions) do depend on which concrete triple went where.

A cheap, sound refutation test over partial bags

During the composition search, every triple constraint tc carries an interval [lo(tc), hi(tc)]: lo triples already committed to it by classes decided so far, and up to hi = lo + potential once every remaining, not-yet-decided class that has tc as a candidate is also counted. A feasibility predicate F(lo, hi), computed compositionally over the expression's tree structure, answers: could some exact bag between lo and hi, pointwise, be accepted? It is necessary but not sufficient — a true answer does not guarantee a satisfying completion exists, but a false answer proves none does, because every exact bag reachable by finishing the search lies between the current lo and hi.

F is applied twice: once, upfront, as an arc-consistency pass — for every candidate (t,tc) pair, is F still satisfiable if tc is committed to lo=1 and every other not-yet-placed triple is optimistically available? If not, delete tc from every triple of its class, all at once (§3's structural generalization) — and again, at every node of the composition search, to cut whole subtrees as soon as a partial choice cannot be completed.

If a class loses every candidate this way, no matching exists at all: a triple whose predicate is mentioned by the expression can never be left unmatched, not even when its predicate is excused for EXTRA — EXTRA only excuses triples that match no constraint in the first place. So the moment arc consistency empties a class, the answer is "does not conform," with nothing left to enumerate.

F deliberately does not decide two families of constraint that a bag abstraction cannot express as independent per-constraint intervals: count coupling inside a repeated group ((a . ; b .)+ requires equal counts of a and b) and divisibility ((a . {2,2})* accepts only even counts). Surviving compositions are therefore always re-checked, once, by the exact interval verifier before being accepted — F only ever discards states that verifier would also have rejected, so completeness is preserved; it just avoids the cost of enumerating and individually re-checking a combinatorial number of states that never had a chance.

Worked example: a FHIR research blood-pressure profile

The techniques of §3 and §4 address different failure modes, and a schema built entirely from one of them (as most textbook examples are) only shows one technique at work. The schema below is written to need both at once, and is deliberately modelled on a real FHIR pattern — a research Observation profile for blood pressure — rather than an arbitrary abstract grammar. It is illustrative, not a certified clinical profile: the element names and general structure (component, referenceRange, both repeatable and both discriminated by a nested shape rather than a bare value) are real FHIR, but the exact codes and the "two acceptable protocols" framing are simplified for the example.

The profile accepts submissions from two data-collection protocols, distinguished along two independent axes. A quick capture records one or two component entries (e.g. a single systolic/diastolic reading, or one retake) and nothing else; an extended capture records any number of component entries but must additionally include one component flagged as a protocol quality-control marker. Separately, and by the same shape, the profile's referenceRange entries are either a short list of directly-applicable guideline ranges, or an extended list plus one range specifically flagged as the critical/out-of-bounds range. Neither the components nor the ranges declare which protocol was used directly; a validator has to work it out from what is present. 

PREFIX fhir: <http://hl7.org/fhir/>
PREFIX ex:   <http://example.org/research-bp#>
PREFIX xsd:  <http://www.w3.org/2001/XMLSchema#>

ex:VitalsPanelShape {
  (
    fhir:component . {1,2}
    |
    fhir:component . + ; fhir:qualityFlag [ex:protocol-qc-check]
  ) ;
  (
    fhir:referenceRange {
      fhir:low  xsd:decimal MININCLUSIVE 60 MAXINCLUSIVE 90 ;
      fhir:high xsd:decimal MININCLUSIVE 90 MAXINCLUSIVE 140
    } {1,2}
    |
    fhir:referenceRange {
      fhir:low  xsd:decimal MININCLUSIVE 60 MAXINCLUSIVE 90 ;
      fhir:high xsd:decimal MININCLUSIVE 90 MAXINCLUSIVE 140
    } + ;
    fhir:referenceRange {
      fhir:low  xsd:decimal MININCLUSIVE 120 ;
      fhir:high xsd:decimal MININCLUSIVE 180
    }
  )
}

Two independent EachOf-sequenced OneOf groups, structurally identical to each other and each identical in shape to the "shared-predicate OneOf" pattern: a \{1,2\} branch competing with an unbounded branch that requires a second, distinctively-flagged element. The component group leaves every candidate component value unconstrained (. — a quick capture's readings and an extended capture's readings look identical by value; only their count and the presence of the QC-flagged component distinguish the protocols). The referenceRange group instead discriminates candidates by value — a guideline range and a critical range have numerically distinct low/high windows. This one difference is what makes the two groups exercise different halves of the machinery, as §5.2 shows with measured numbers.

The two views, concretely, at a small instance

Take 3 component triples (values "reading-0", "reading-1", "reading-2", no fhir:qualityFlag anywhere) and 2 referenceRange triples, both with low/high inside the guideline window (say [65,100] and [70,110]) and outside the critical window. Write TC_A = fhir:component . {1,2}, TC_B = fhir:component . +, TC_C = the QC-flag constraint, TC_D = the guideline-range shape constraint, TC_E = the critical-range shape constraint. The pre-matching (T → 2^{TC}) is: 

reading-0  → { TC_A, TC_B }
reading-1  → { TC_A, TC_B }
reading-2  → { TC_A, TC_B }
range-0    → { TC_D }        <- TC_E already refuted: see below
range-1    → { TC_D }        <- TC_E already refuted: see below

Read the other way (TC → 2^T): before value-checking, TC_D and TC_E both nominally claim \{range_0,range_1\} (same predicate, fhir:referenceRange); after checking each range's low/high against each candidate shape's numeric window — the recursive value check that negative caching performs once per pair — TC_E is refuted for both, because neither range's bounds reach the critical window's minimum of 120/180. This refutation happens before any structural reasoning about cardinalities runs at all, and it is why the pre-matching above already shows only TC_D for both range triples.

The component triples get no such help: every reading's value satisfies both TC_A and TC_B (. accepts anything), so no (t,tc) pair among them is refuted by value. Take the matching \{reading_0{\to}TC_A,\ reading_1{\to}TC_B,\ reading_2{\to}TC_B\} as an example candidate. Its split (the TC → 2^T view of this specific matching) is TC_A{\to}\{reading_0\}, TC_B{\to}\{reading_1,reading_2\} — both individually within bounds (1 ∈ [1,2]; 2 ≥ 1) — but both branches of the component OneOf are simultaneously non-empty, which OneOf forbids outside a repetition. Rejected, and not because any single count is wrong — exactly the same ensemble-level failure mode as before, now happening inside a FHIR-shaped schema instead of an abstract one.

Two techniques, two different jobs, measured

Generalize to n_c component triples (no QC flag) and n_r referenceRange triples (all inside the guideline window, none inside the critical one). The naive Cartesian enumeration (MatchingsIterator) would check 2^{n_c} \times 2^{n_r} = 2^{n_c+n_r} matchings — both groups multiply together, because the historical algorithm enumerates the whole neighbourhood's candidate choices at once, regardless of which predicate a triple has. Measured on the reference implementation (a Jena-based probe structurally identical to MatchingSearchProbesTest), counting how many matchings reach the final exact verifier (informCandidateMatchingConformance):

Components alone check 0 — the same structural refutation as the abstract example: no candidate is refutable by value (every reading satisfies both TC_A and TC_B), so the feasibility predicate F (§4.2) has to do all the work — and it does: the QC-flag constraint's zero potential makes the extended branch infeasible the moment any triple commits to TC_B, collapsing every triple onto TC_A alone, which then fails its maximum of 2. No matching is ever assembled at all.

Ranges alone check 2 n_r, not 0 — and that nonzero, linear figure is the honest signature of negative caching rather than a failure of it. Each of the n_r range triples nominally has two candidates sharing predicate fhir:referenceRange; before either is prunable, each candidate's own nested triple expression (its low/high constraints) has to be checked once against that range's actual values — one recursive check for the guideline-shaped candidate, one for the critical-shaped candidate, both of which resolve to a single (trivial, non-ambiguous) matching of their own two facets and so each register once in the count. That is exactly 2 checks per range triple, 2n_r total — and, critically, it does not depend on n_c at all (compare the 16/16 row above, 32 checked, to the 0/16 row here, also 32): whatever combinatorial explosion the component group is contributing elsewhere in the schema, the cost of ruling out the critical-range candidate stays flat. Without negative caching, an implementation re-deriving "this range's bounds don't reach 120" once per candidate matching that would have tried it — rather than once per candidate pair — would pay that cost 2^{n_c} times over for every one of the n_r ranges, multiplying into the same exponential the component group already produces on its own.

Put the two together and the story is precise, not just qualitative: negative caching holds the value-discriminable dimension ( ranges) at a constant-per-triple, linear total cost, independent of everything else in the schema; feasibility bags collapse the value-indistinguishable dimension (components) to zero, however large it grows. Neither alone explains the measured 32 at n_c{=}n_r{=}16 — it is exactly 0 + 2{\times}16, the two techniques' contributions added, against a naive baseline of 2^{32}.

As a positive control, n_c{=}n_r{=}2 conforms (2 readings fit the quick protocol's \{1,2\}; 2 guideline ranges fit the short-list branch): the optimized search checks 5 matchings and accepts one of them — real search work happens for genuinely satisfiable instances, as it must; the pruning only ever discards states that could never have led anywhere.

Summary for implementors

  • Represent the candidate-matching problem as a map from triples to their candidate triple constraints (§2), not the reverse; recover the constraint-indexed view only after a matching has been chosen, for the checks that need it.
  • Prune a candidate the moment it is refuted, whether by a per-triple value check (§3) or by a structural, ensemble-level infeasibility (§4) — and never re-derive a refutation the search has already made once.
  • Group triples by identical candidate sets and search count distributions ("bags"), not individual assignments; verify only bags that survive a cheap, sound feasibility test with the exact (and only then expensive) interval computation.
  • Both pruning techniques are necessary, not decision, conditions: they discard only states that could never lead to an accepted matching. The set of matchings a validator accepts is unchanged by adding them; only the amount of work spent finding that out changes.
